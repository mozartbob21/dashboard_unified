# Коллективные жалобы: общее серверное хранилище

Обновление на основе архива «Дашборд_коллективки_МО.zip». Использует существующий раздел `/mingkh/collective`, сессию Нейроны и независимое право `collective`. Новый EXE не запускается и не поставляется с платформой. Сохраняются три темы, действующая выгрузка из `cur.bi.mosreg.ru` и шаблон презентации.

## Работа пользователя

1. Выберите период. Сохранённая выгрузка открывается сразу; если её ещё нет, запускается сбор из МинЖКХ. Кнопка «Обновить» запрашивает источник повторно. Длительная загрузка выполняется на сервере и продолжается после закрытия вкладки.
2. Откройте обращение. Ответственный и ручная тема сохраняются сразу; текст доклада — кнопкой «Сохранить доклад». Ограничение доклада — 20 000 символов. Обновление из источника не заменяет эти поля.
3. Свод «По ответственным» и фильтр «Не распределённые» помогают контролировать работу. Открытые обращения, уже назначенные и обращения, поступившие с момента начала распределения, доступны для назначения. Это правило проверяется сервером.
4. Администратор с правом управления пользователями добавляет ответственных, архивирует и возвращает их. Архивный сотрудник остаётся в прежних назначениях, но не доступен для новых назначений. Отдельного права `mingkh` для работы в коллективных жалобах не требуется.
5. Excel и презентации включают сохранённые доклад и ответственного. Презентация берёт исходные поля и ручные данные из серверного снимка по ключам выбранных обращений.

При конфликте двух редакторов сервер возвращает актуальную версию: интерфейс сохраняет набранный текст и предлагает сравнение перед повторной отправкой. При сетевой ошибке можно повторить сохранение. Несохранённый доклад остаётся в памяти открытой страницы; закрытие карточки и уход со страницы предупреждают о нём. До нажатия «Сохранить доклад» черновик не переносится на другое устройство.

Страница сверяет сохранённые данные с сервером каждые 60 секунд и при возвращении во вкладку. Синхронизация приостанавливается, пока открыта карточка, выполняется операция или есть несохранённый доклад. Она не делает новый запрос в МинЖКХ. Источник обновляется отдельной кнопкой.

## Хранение и перенос

В существующей `data/dashboard.db` создаются таблицы `collective_*`: снимки периодов, стабильные идентификаторы обращений, ручные поля, справочник, последние 20 редакций и состояния фоновых обновлений. Не удаляйте рабочую БД при переносе кода. Резервное копирование выполняется штатным способом платформы; база содержит данные обращений и доступна только серверу.

Схема применяется автоматически при первом обращении к разделу, повторное применение безопасно:

- `migrations/20261019_collective_workspace.sql` — данные и ручная работа;
- `migrations/20261019_collective_refresh.sql` — фоновые обновления.

Для предварительного применения на остановленном сервере из каталога проекта можно выполнить Python из виртуального окружения:

```python
from services.collective import store, refresh
store.initialize()
refresh.initialize()
```

Перед обновлением сохраните резервную копию рабочей БД. GitHub переносит код, миграции и описание релиза; рабочие данные и учётные данные остаются исключёнными из Git. Деплой в рамках разработки не выполняется.

В переданном ZIP находятся EXE и инструкция, но нет выгруженных обращений или файла распределения. Если ранее использовалась отдельная программа, администратор может перенести её `распределение.json` через справочник «Ответственные». Импорт атомарный, повторный перенос не создаёт дубликатов и не заменяет уже внесённые в Нейроне правки. Ручные темы из старого браузера переносятся отдельной явной кнопкой для выбранного периода; после переноса они общие для коллег.

## Доступ и надёжность

Все API, включая чтение снимков, статусы заданий, изменение карточек и выгрузку, проверяют право `collective`. Изменение справочника и импорт требуют дополнительных прав администратора. Редактор определяется из серверной сессии. Пароли МинЖКХ используются только сервером; они не попадают в задания или браузер.

Единовременно выполняется один сбор коллективных жалоб. Одновременные запросы того же периода объединяются. Повтор с тем же `Idempotency-Key` возвращает прежнее задание; другой период при занятом сборе получает понятный ответ. При ошибке источника или перезапуске предыдущий снимок и ручные данные сохраняются. Блокировка сборщика поддерживает Windows и Unix, но проверка разработки проводилась на macOS.

## Проверка

Тесты используют временную SQLite и синтетические ответы источника, без обращения к рабочему порталу:

- `test/test_collective_store.py` — хранение, версии, импорт, архив и конкурентность;
- `test/test_collective_workspace_api.py` — права, общие данные, фоновые задания и серверные поля в экспорте;
- `test/test_collective_manual_presentation.py` — доклады, безопасный текст и длинные презентации;
- `test/test_collective_frontend.js` — состояния интерфейса, ошибки сети, конфликты, синхронизация и экспорт;
- существующие тесты `test_collective*.py` — протокол источника, классификация и качество презентаций.

Проверка на рабочем Windows-сервере с реальным доступом к МинЖКХ требуется после переноса кода. Локальная проверка интерфейса использует отдельный сервер, тестовые обращения и отдельную БД.

## Дополнение 19.10.2026: расположение таблиц и смена периода

«По ответственным» находится над ОМСУ. Список справа занимает высоту обеих таблиц; на узком экране блоки идут последовательно.

При первом выборе периода `GET /mingkh/collective/api/data` может вернуть 404: это отсутствие сохранённого снимка, после которого интерфейс запускает фоновую загрузку. Сам по себе такой 404 не объясняет ошибку сохранения.

Исправлен воспроизведённый конфликт: два разных основных номера обращения могли иметь один номер исходной системы. Теперь основной номер имеет приоритет; расширение периода не объединяет такие обращения и не теряет ручные поля. Если прежнюю запись без основного номера нельзя однозначно сопоставить, загрузка отклоняется атомарно с объяснением. В журнале остаются тип и код ошибки без содержимого обращений и паролей.

Добавлена отдельная миграция `migrations/20261019_collective_secondary_index.sql`. Она применяется через `store.initialize()` автоматически при первом обращении к разделу: восстанавливает производный индекс номеров из сохранённых исходников и псевдонимов, если установка была промежуточной/неполной. В исправной базе прежние записи не изменяются. Не запускайте этот SQL отдельно: заполнение индекса и отметка миграции должны проходить вместе в одной транзакции.

Проверки воспроизводят конфликт номеров и неполную схему на синтетических данных. В первой опубликованной Git-версии таблица уже есть; поэтому дефект промежуточной базы не объявляется доказанной причиной сбоя сервера. По одной строке 404 установить рабочую причину нельзя. Новый безопасный код диагностики помогает различить ошибки источника, проверки данных и прочие сбои.


Итоговый общий прогон этой доработки: 487 Python-тестов, 124 дополнительных сценария и 62 JavaScript-теста прошли. В том числе `test_collective_period_refresh.py` проверяет конфликт вторичных номеров, а `test_collective_secondary_upgrade.py` — безопасное восстановление производного индекса, повторное применение и откат при сбое. Интерфейс проверен в браузере на временных данных; живой портал и Qwen не вызывались.
