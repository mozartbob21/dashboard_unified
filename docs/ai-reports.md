# Отчёты ИИ по данным платформы

В AI-чате достаточно написать обычное сообщение: «Дай краткий отчёт по всем блокам», «Покажи камеры и просрочку по Химкам», «Дай отчёт по Власихе и Балашихе в ЕДДС и МинЖКХ» или «Сводка по каждому муниципалитету в блоках ЕДДС и МинЖКХ». Отдельного переключателя и формы выбора нет. Можно назвать один или несколько блоков и муниципалитетов, попросить разбивку по всем округам. Если написать «об этом блоке» без предшествующего отчёта, чат попросит название. Ссылки на чат из карточек подготавливают текст сообщения; ничего не отправляют автоматически.

Уточнения «Подробнее», «А по камерам?» и «Теперь вся область» продолжают последний отчёт. Короткое «А теперь по Химкам» меняет муниципалитет и сохраняет выбранные блоки. Новый запрос по муниципалитету охватывает все доступные блоки, если в тексте не названы конкретные; запрос «по всем блокам» сбрасывает прежнее ограничение блока и муниципалитета. Приветствия, обычная переписка и анализ приложенного файла не читают результаты платформы автоматически. Совместимость с API `include_context=true/false` и `context_module/source/municipality` сохранена для старых клиентов.

Данные читаются заново при **каждом запросе отчёта**, включая уточняющие вопросы. Ответ не запускает сбор с порталов. Обновите нужный дашборд перед отчётом, если требуется новая проверка. Для источников передаются сохранённые даты, период, статус и ошибки, когда они есть. Дата сборки контекста не подменяет дату исходных данных. Областной показатель не подставляется вместо муниципального; отсутствующее значение не считается нулём. При большом объёме количество пропущенных строк указано явно; каждый выбранный доступный источник остаётся в контексте.

После переноса обновления через GitHub перезапустите Нейрону и обновите страницу сочетанием Ctrl+F5. Один раз успешно обновите данные ЕДДС, МинЖКХ, ЕЦУР и проверки задач РМ Водоснабжения, чтобы появились новые сохранённые снимки. Результаты остальных уже работающих модулей читаются сразу; дополнительные пакеты для этой функции не нужны.

## Подключённые данные

- Сводный дашборд использует тот же `data/water_dashboard/snapshot.json`, `schema_version=3`, и `normalize_snapshot()` / `source.details`, что и карточки. Передаются семь действующих источников, их проверенные показатели и рейтинги. Промывки сетей и РЧВ исключены.
- ЕДДС: `data/edds/arm-summary.json` сохраняется после успешной выгрузки АРМ и содержит агрегаты инцидентов ВС/ВО, активных и закрытых заявок, период и дату сбора. Охват жителей — сумма охватов инцидентов, а не число уникальных людей. Жалобы Добродела читаются отдельно из `data/edds/water_daily.json`; непокрытые дни или муниципалитеты не выдаются за ноль жалоб.
- МинЖКХ: `data/mingkh/report-summary.json` сохраняет безопасные агрегаты успешной загрузки дашборда: количество обращений по муниципалитетам и периодам. В архив не включаются тексты обращений или доступы. Старые установки получат этот файл после следующей успешной загрузки данных. Карта читается из `data/mingkh/water-map.json.gz`; количество записей карты не подменяет полное количество обращений дашборда, а архивная версия помечается как сохранённая.
- Остатки ЗиП: только согласованные опубликованные строки `data/zip_curator/published.json`. Количество позиций и РСО не подменяет сумму запасов; разные единицы не складываются. Несогласованные данные не читаются.
- ЕЦУР: безопасная сводка `data/ecur/report-summary.json` сохраняется после успешного сбора и содержит дату сбора, фильтры выборки и агрегаты жалоб. Отчёт не включает тексты обращений и доступы.
- РМ Водоснабжение: `data/water_rm/last_check.json` хранит разрешённые поля последней проверки. Рекомендации по задачам не означают, что изменения уже применены. Муниципалитет определяется по отдельному полю или названию проекта только при точном совпадении со справочником; неизвестная принадлежность не угадывается.
- Обращения 1С, заполненность данных, просрочка, контроль воды, технадзор, ЖКХ Redmine и камеры: разрешённые операционные поля их сохранённых результатов. Если формат не содержит муниципалитета, муниципальные показатели не придумываются.

Если блок ещё не выполнял успешную проверку после обновления, его данные будут отмечены как отсутствующие. Новые аналитические блоки без подключённого сохранённого источника явно перечисляются в ограничениях. Инструменты, переписка и генераторы текстов не считаются аналитическими источниками. Для нового формата нужен отдельный адаптер и тесты; сборщик не обходит папки и не читает произвольные файлы.

## Контракт и защита данных

Контекст — JSON `schema_version=2` с `assembled_at`, `selection`, `sources`, `coverage`, `limitations`. В `selection` хранятся массивы `modules`, `sources`, `municipalities`, `group_by`, а одиночные поля сохранены для старых клиентов. Несколько округов передаются таблицей `municipality_table`, где областные итоги удалены. Названия муниципалитетов нормализуются по общему справочнику; «г.о. Химки» и «Химки» не становятся двумя округами.

В контекст не включаются конфигурация, учётные данные интеграций, браузерные профили, необработанный HTML, персональные сообщения и контакты ответственных. Права на модули проверяются заново перед чтением, в том числе при продолжении общего диалога. Общая история диалогов и уже созданные ответы остаются видны всей организации — это намеренное поведение.

Новый внешний сервис не требуется: используется уже настроенный в проекте локальный ИИ / разрешённый Госчат. Правила отчёта задаются системным сообщением; структурированный контекст передаётся отдельно как справочные данные и не становится системной инструкцией. При сбое ИИ выводится понятная ошибка с кодом и номером запроса; сохранённые числа не подменяют ответ модели. Технические ошибки остаются в общей истории, но не передаются модели при следующем запросе. Качество формулировок конкретной модели требует проверки на офисном сервере.

Проверки выполняются локально: естественные запросы, несколько блоков и округов, отсутствие залипания выбора, разделение областных и муниципальных данных, пропуски покрытия, свежесть повторного чтения, сохранение общей истории, повторная проверка прав, исключение секретных полей, ограничение объёма и реальный HTTP-маршрут чата с подменённым транспортом ИИ. Тесты не обращаются к ИИ и внешним порталам.


## Обычный чат и подключение Qwen

Чат остаётся универсальным помощником: вопросы, объяснения, тексты, переводы, идеи, код и файлы. Аналитика включается по смыслу запроса, когда названы данные платформы, блоки или муниципалитеты. Само слово «отчёт» или «информация» не включает отчёт по платформе. Новая тема после отчёта продолжает обычный диалог.

Используются существующие настройки серверного `.env`: `QWEN_API_BASE`, `QWEN_API_KEY`, `QWEN_MODEL`. Для адреса также поддерживается `QWEN_BASE_URL`; если заданы оба адреса, приоритет у `QWEN_API_BASE`. Переустанавливать пакеты или переносить ключи из-за этого исправления не требуется. После обновления кода перезапустите процесс Нейроны и обновите страницу Ctrl+F5. Пароли и ключи не следует присылать в чат или включать в Git.

Запрос к модели содержит одно системное сообщение, чередующиеся сообщения пользователя и ИИ и текущий вопрос в конце. Приветствие интерфейса и технические ответы в запрос не включаются. Данные отчёта добавляются к текущему вопросу, отдельно от инструкций. Если Qwen вернул только `reasoning_content`/`reasoning`, выполняется ограниченный повтор; пользователю возвращается только итоговый текст.

При повторном сбое администратор увидит в чате код `AI_*` и номер запроса. Та же пара записывается в лог `aichat` вместе с классом исключения и HTTP-статусом, без ключей, текста запросов и тела ответа провайдера. `AI_AUTH_FAILED` — отказ в ключе, `AI_REQUEST_REJECTED` — несовместимый запрос или настройки, `AI_CONTEXT_LIMIT` — превышен объём контекста, `AI_CONNECTION_ERROR`/`AI_TLS_ERROR` — соединение или сертификат, `AI_EMPTY_RESPONSE` — модель не вернула итоговый текст. Эти сообщения описывают фактический сбой; наличие настроек в `.env` само по себе не доказывает доступность модели.


### Диагностика авторизации Qwen

Если все функции Qwen возвращают `AI_AUTH_FAILED`, сервис отвечает HTTP 401. Формат авторизации остался прежним: общий `QWEN_API_KEY` отправляется как Bearer. Ключи из окружения Windows имеют приоритет над `.env`; обновлённый ключ в файле может перекрываться старой переменной процесса. Сумматор дополнительно поддерживает `SUMMARIZER_QWEN_API_KEY`, поэтому его настройки могут отличаться.

В активированной среде сервера из папки проекта выполните:

```powershell
python scripts/check_qwen.py --probe
```

Без `--probe` выполняется только чтение конфигурации. С ним отправляется короткий тестовый вопрос без истории, документов и данных модулей. Если в сумматоре задан отдельный ключ Qwen, он проверяется отдельно. Вывод содержит только признаки наличия/конфликта настроек и код результата; ключи, адреса, модель и ответ ИИ не печатаются. `conflict: true` означает, что переменная процесса перекрывает другое значение `.env`. Скрипт ничего не изменяет. Изменение файла требует перезапуска приложения; при конфликте следует также устранить старую переменную запуска. Если конфликта нет, а ответ остаётся 401, нужно проверить действительность ключа в самом сервисе.
