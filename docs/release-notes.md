# Что нового в сервисе

«Что нового» — список изменений выпуска. Колокольчик системных уведомлений убран из шапки главной страницы вместе с его фоновыми запросами. История обновлений доступна через меню профиля. Уведомления управляющих аккаунтами в админ-панели не меняются.

В каталоге хранятся только изменения текущей версии продукта. При выпуске новой версии описания предыдущих версий удаляются из каталога. Сейчас опубликована **«Нейрона ИИ — версия 3.1»**: мобильный интерфейс, единое оформление и приоритеты показателей сводного дашборда. Общие изменения доступны всем авторизованным пользователям, изменения сводного дашборда — только с правами соответствующего блока.

После обновления интерфейс запрашивает непрочитанные выпуски текущей версии. Сервер возвращает только изменения блоков, к которым у аккаунта есть доступ. Повторно открыть список изменений можно через **«Что нового»** в меню профиля.

Выпуск отмечается на сервере при подтверждении/закрытии окна. Чтение API само по себе ничего не отмечает. Состояние общее для устройств одного аккаунта и независимо у разных аккаунтов. Ошибку сохранения можно безопасно повторить. Подтверждение одной вкладки не закрывает уже открытое окно другой вкладки, но следующие запросы на обоих устройствах увидят отметку.

## Как добавлять изменения после каждой работы

1. Откройте `services/release_catalog.py`.
2. Добавьте отдельный выпуск с **новым уникальным `id`**, датой, версией и понятными пользователю пунктами. Например: `2026-10-16-zip-validation`. Несколько обновлений в один день должны иметь разные ID. `version` — версия продукта (например, `3`), а `published_at` — отдельная дата выпуска; не подменяйте одно другим.
3. Для пункта укажите аудиторию: `audience: "module"` и канонический `module_id` (например, `zips`, `mingkh`, `summarizer`); `audience: "all"` для общих изменений; `audience: "admin"` для пользователей с серверным правом управления аккаунтами.
4. Заголовок выпуска должен быть нейтральным: «Обновление сервиса». Названия конкретных блоков и подробности помещайте в пункты с соответствующей аудиторией.
5. Опишите готовый результат простыми словами. Не копируйте сообщения коммитов, внутренние адреса, секреты или рабочие данные. Тексты — обычный текст, без HTML.
6. Проверьте тесты и передайте каталог через Git вместе с кодом изменений. После установки версии перезапустите сервер обычным способом.

**ID опубликованного выпуска не переиспользуется.** Для нового уведомления добавляйте новый `id`. При смене версии продукта удаляйте из каталога выпуски предыдущих версий, не удаляя пользовательские отметки о прочтении из БД. `published_at` описывает выпуск, но не служит расписанием будущего показа: доступность определяется установленным каталогом.

Каталог — отслеживаемый Python-файл. Рабочие JSON-файлы, базы, пароли и состояние пользователей в Git не добавляются. Приложение не читает Git во время работы и не генерирует заметки из коммитов.

## Хранение и миграция

В существующей SQLite-базе `data/dashboard.db` создаётся таблица `release_note_receipts`: `account_key` (`local:<id>` либо `keycloak:<sub>`), `release_id`, `read_at` (UTC). Первичный ключ `(account_key, release_id)` защищает от дублей. `INSERT OR IGNORE` сохраняет время первого подтверждения.

Миграция `migrations/20261015_release_notes.sql` автоматически применяется при первом запросе API. Она идемпотентна и не изменяет аккаунты, настройки, результаты опросов и обычные уведомления. При необходимости применить её заранее из корня проекта:

```powershell
python -c "from services.release_notes import initialize; initialize()"
```

Команда использует существующую базу приложения. Отдельная инфраструктура не нужна. Не удаляйте базу или отметки ради повторного уведомления — выпускайте новый `id`.

## API и права

Все методы требуют авторизацию. Локальные права и активность аккаунта перечитываются из БД в каждом запросе. Прежние права в браузере или токене не расширяют доступ. Для Keycloak используется действующая модель прав платформы. Локальная роль «Администратор» сама по себе не открывает закрытые блоки.

- `GET /api/releases/pending`: `{releases: [...], pending_count: N}` с непрочитанными доступными выпусками.
- `GET /api/releases/history`: та же структура, включая прочитанные доступные выпуски; `pending_count` — число непрочитанных.
- `POST /api/releases/{release_id}/read`: без тела либо с `{}`. Ответ `{ok: true, release_id: "...", read_at: "..."}`. Параметры пользователя в теле запрещены.

Выпуск содержит `id`, `version`, `title`, `published_at`, `read_at`, `entries`. Пункт содержит `id`, `module_id`, `module_name`, `title`, `text`. До подтверждения `read_at` равен `null`. Ответы не содержат идентификатор аккаунта, логин или почту.

Выпуск без доступных пунктов не возвращается. Неизвестный и полностью недоступный выпуск при подтверждении дают одинаковый `404`. Неавторизованный запрос API даёт `401`; глобальная авторизация приложения также может перенаправить GET на страницу входа, поэтому клиент проверяет тип ответа. Успешные ответы содержат `Cache-Control: private, no-store`. После отзыва прав соответствующие пункты скрываются и в истории.

## Проверка

```powershell
python -m pytest -q test/test_release_notes.py
```

Тесты используют временную SQLite-базу и настоящий роутер с подставленной авторизованной личностью. Они не запускают приложение целиком, не читают рабочие учётные данные и не обращаются к внешним сервисам.

Проверяются права блоков и управляющих, отзыв доступа, отключение аккаунта, разделение Keycloak, состояние между клиентами, повторные подтверждения, параллельная первая миграция и отправка, защита от чужого `user_id`, повтор после ошибки записи, независимость нового выпуска и сохранность обычных уведомлений. Проверка вида окна и сетевого поведения относится к фронтенду.
