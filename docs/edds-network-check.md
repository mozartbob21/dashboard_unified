# Проверка сети АРМ ЕДДС

Запускайте проверку на компьютере, где работает сервер «Нейроны», из корня проекта:

```sh
python -m services.edds.diagnose > edds-network-check.json
```

Скрипт проверяет системный DNS, ответ указанного DNS, TCP и TLS с проверкой
сертификата. Он не читает сохранённые пароли и не выполняет вход.
Логины и пароли прокси не выводятся.

Адреса `10.10.34.2` и `10.10.51.2` используются как переданные для диагностики
внутренний адрес портала и DNS. При необходимости их можно задать аргументами
`--internal-ip` и `--dns-server`. Скрипт не меняет DNS, hosts или VPN компьютера.

Проверка 17.09.2026 на текущем Mac:

- Системный DNS вернул `185.120.188.34`.
- Первые запросы к `10.10.51.2` по UDP и TCP также вернули `185.120.188.34`.
  Повторная проверка TCP-доступа к этому DNS закончилась тайм-аутом; доступ нестабилен.
- `10.10.34.2:443` не ответил за 5 секунд.
- `185.120.188.34:443` принял TCP-соединение, но HTTPS не завершился успешно.
- Принудительный запрос HTTPS к `10.10.34.2` с именем
  `zkh-kontur.mosreg.ru` также завершился тайм-аутом подключения.

Эти результаты относятся к текущему компьютеру, а не к другому рабочему ПК
или Windows-серверу. Доступность внутреннего адреса из рабочего сегмента
следует подтвердить отдельно; один ответ DNS не доказывает правильность адреса.

## Текст обращения в ИТ

«Просим проверить доступ с компьютера-сервера “Нейрона” к АРМ ЕДДС
`https://zkh-kontur.mosreg.ru/new9/`. Предполагаемый внутренний адрес
`10.10.34.2:443` не отвечает, а запрос к DNS `10.10.51.2` возвращает внешний
адрес `185.120.188.34`. Просим подтвердить актуальный внутренний адрес,
настройку внутреннего DNS и разрешённый маршрут из сегмента сервера.
Результат диагностики приложен».

Если сеть доступна, но не проходит проверка сертификата, используйте доверенный
CA bundle, предоставленный ИТ. Проверка сертификатов должна оставаться включённой.
Для блока АРМ путь задаётся переменной `EDDS_ARM_CA_BUNDLE`.
